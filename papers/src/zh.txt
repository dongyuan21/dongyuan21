# 1 研究背景与系统贡献

## 1.1 变体制作中的两类困难

消除类游戏广告通常围绕已有创意制作多个版本，修改内容包括牌面、材质、牌堆排列、消除特效、操作顺序和演出节奏。制作人员需要在沿用已有设计的同时尝试新的组合。

团队曾使用视频生成和编辑模型直接处理成片，相关技术包括参考驱动生成、视频编辑和遮罩编辑[2]。牌面等修改目标虽只占部分画面，却要在移动、遮挡、进入托盘和消除过程中保持身份与替换关系。局部画面修改正确，还需要在整段视频中持续成立。

玩法过程带来了另一类要求：对象能否点击、选择如何改变托盘或棋盘、哪些组合允许消除，都应符合所声明的规则。视觉连续性和玩法合理性分别影响成片是否可用。基于这些生产经验，我们将后续修改转向可操作的项目和对象，沿用其中无需改变的内容。

## 1.2 被低估的专业设计源工程

团队保留了大量 After Effects 合成、Blender 场景和历史 Cinema 4D 资产。它们保存了成片中已被合并的牌层、对象、材质引用、动画、特效和事件安排，但这些设计成果尚未得到充分复用。源工程既代表已经投入的设计工作，也提供了可直接使用的编辑入口。

Agent 调用专业软件工具，在工程副本中替换指定内容，并沿用未受影响的动画、牌体和合成关系。已有工作流覆盖牌面、材质和特效改造；参考布局任务还会检查重排后的层级、遮挡与交互关系[3,4]。

随着任务增加，分散在不同工程中的素材需要统一查找和复用。适合独立使用的内容被提取并整理到元素库，供 Agent 按文字要求或视觉参考检索、选用和拼装。难以拆分或适合整体使用的内容，继续以完整工程保留。

## 1.3 从工程改造扩展到领域化生产

已有母版的布局、时间线和实现方式限制了可调整的范围。为支持新局面、不同动作和消除节奏，团队构建了 melo-gcs[1]，将这些操作组织为领域接口。外部 Agent 通过命令行接口（CLI）调用既有能力，在同一项目上持续编辑。

melo-gcs 使用 Chromium GPU 渲染正式视频，无头模式支持在没有可见工作界面的情况下执行任务。设计师审阅输出，浏览器表现不能满足要求时，再通过专用导入工作流生成 After Effects／Blender 原生工程继续精修。本文以 Skill 指代编排工具调用的一组可复用指令。数字内容创作（Digital Content Creation，DCC）软件由此兼顾已有设计的利用与后续精修。

缺少源工程时，外部 Agent 可以根据参考视频调用 melo-gcs CLI 建立项目。项目保存后，后续修改继续作用于其中的对象、玩法和元素关联，沿用相同的浏览器制作流程。

## 1.4 报告问题与三项系统贡献

本报告研究如何利用未充分复用的专业设计成果，结合领域软件与外部 Agent，形成直接视频生成之外的持续编辑和批量生产路线。系统通过完整源工程与局部元素两种粒度保留已有设计，在 melo-gcs 项目中组织玩法记录、演出时间和元素关联，并提供相应的领域操作。参考视频进一步扩展了缺少源工程时的接入方式。三个制作案例和一组生产观察用于说明系统的实际使用，贡献集中在以下三个方面。

存量设计成果的分层复用。支持完整专业工程的定向改造，也将适用素材和组件提取入库，供后续任务检索与组合。

面向 Agent 的玩法与表现编排。melo-gcs 项目保存玩法、演出和元素关联，原子 CLI 提供外观、布局、动作及节奏编辑；外部 Agent 负责方案与调度，melo-gcs 执行领域操作。

浏览器生产与按需专业精修。melo-gcs 通过 Chromium GPU 和无头模式输出视频；浏览器结果无法满足设计要求时，再转入 DCC 工作流。报告结合硬件运行情况和 18 组共 72 条视频的生产记录，分析这一分工的实际使用。

# 2 相关工作与技术基础

## 2.1 视频生成与项目化编辑

VACE 以统一条件接口支持参考生成、视频到视频编辑和遮罩编辑[2]，可以直接处理视觉素材。本系统的视频输入路线先建立可编辑的 melo-gcs 项目，再由领域软件渲染和修改；源工程输入路线则直接利用已有对象与设计关系。

两类输入各有准备成本：源工程可能依赖特定素材和软件环境，视频重建需要识别对象、动作与表现。本文考察内容接入后的复用与编辑方式。

## 2.2 创作智能体与专业软件控制

BlenderAlchemy 研究视觉语言模型驱动的图形编辑[5]；BlenderGym 评估代码驱动的图形编辑系统[6]；FilmAgent 探索虚拟三维空间中的多 Agent 影片制作[7]。这些工作提供了模型决策与创作工具相结合的先例。

本文关注一次创作的结果如何成为下一次任务的可编辑输入。专业软件控制用于继承已有设计，melo-gcs 项目则表达消除玩法动作和演出。复用已校验的玩法记录，使外观变体制作可以与生成新动作序列分开处理。这种面向应用的组织方式补充了上述图形编辑和影片制作研究；本报告未比较这些系统的任务表现。

## 2.3 浏览器制作的基础设施

Chrome Headless 支持没有可见界面的浏览器执行，Chromium 文档也说明了在适用配置下使用 GPU 的方式[8,9]。Three.js 提供 WebGL 渲染器及基于物理的材质组件[10,11]。melo-gcs 在这些基础上组织固定或受限视角的几何、材质、灯光、特效与帧输出。

melo-gcs 利用这些已有基础设施完成项目编辑、玩法编排和批量输出，系统设计重点是制作流程的组织。

# 3 制作任务、项目与交付物

## 3.1 输入与修改要求

系统接受专业源工程、参考视频和已保存的 melo-gcs 项目。文字要求与参考图片补充目标材质、牌面主题或堆叠轮廓；新局面也可直接通过 melo-gcs 配置创建。

每个任务明确输入、目标变化、需要保留的内容和交付规格。换牌面通常沿用原动作，重定时可保留操作顺序，改堆叠或有效动作则需重新处理受影响的状态与交互条件。参考图提供可见布局，隐藏层与完整玩法仍需其他依据。

## 3.2 melo-gcs 项目与元素

melo-gcs 项目是系统中可编辑、可渲染的创作对象，以 JSON 保存玩法、演出和元素关联，构成领域专用描述（DSL）。本文讨论创作对象时使用“melo-gcs 项目”，讨论保存与传递时使用“melo-gcs 项目文件”。

项目记录元素如何组合和使用，元素保留可局部复用的内容及其依赖。贴图、脚本、特效和组件可由多个适用项目引用。专业源工程则保留原生编辑方式，可直接在相应软件中使用。

在公开实现中，一份玩法记录（Take）关联游戏模块、初始状态标识、随机种子和有序动作。语义回放标识包含动作序列，不包含指针采样；帧回放标识在此基础上增加交互、演出时间、帧率与总帧数。创作母版（creative master）记录游戏与规则集版本、回放标识、布局及机位引用和输出配置。

变体配方（variant recipe）选择外观资产及允许覆盖的参数，编译器将这些引用解析为渲染计划[1,12]。这些标识用于跟踪需要保持的状态，不是图像相似度的度量。

## 3.3 交付与验收

浏览器路线交付项目与视频，结果无法满足设计要求时才转入 DCC 原生工程精修。直接修改已有DCC 工程的任务从原生工程开始，可在原软件内完成。

验收包括目标修改、玩法与保持要求、媒体完整性及任务用途。玩法规则符合和视觉结构完整是基础要求，综合验收还涉及主题表达、节奏和投放适配性。未通过的结果按问题类型返回相应编辑环节。

## 4.2 源工程拆分、元素沉淀与召回

Agent 调用专业工具定位牌面、材质、特效或组件，将适用素材连同来源、依赖和使用信息整理入库；不宜拆分的内容以完整工程或组件保留[3,4]。后续任务以文字要求或视觉参考检索候选，选择符合目标项目条件的元素进行绑定和拼装。

元素库负责“拆分—入库—召回—使用”，melo-gcs 运行时资源管理负责解析当前项目所用资源及其依赖[12]。本文介绍两者的接口关系，索引、排序和多模态检索算法不在讨论范围内。

## 4.3 melo-gcs 承接玩法与表现编排

melo-gcs 分别处理玩法、演出和渲染。玩法定义状态、合法动作和规则事件，演出安排动作与反馈时间，渲染将几何、材质、灯光和特效转为画面[1,12]。外观修改由此可以复用已有玩法记录。

接口覆盖方块放置、掉落式方块破坏、托盘叠牌三消和麻将消除四类游戏。各游戏保留自身的规则与动作定义，共用项目制作和工具调用方式。

## 4.4 原子 CLI、组合 Skill 与持续编辑

CLI 提供配置创建、外观应用、玩法记录校验、项目生成和渲染等原子操作。Agent 通过能力自述了解可用工具，读取结构化结果并决定下一步；Skill 组合这些调用，具体操作由 melo-gcs 执行[1]。

melo-gcs 项目维护方提供的官方组合 Skill（melo-remix-looks）生成一份通过校验的 Take，后续各套外观复用同一记录[13]。在其掉落式方块工作流中，skin apply 修改外观，take validate 在新配置下检查原 Take，document emit 保存项目，render 按需输出视频；校验失败即停止该变体。相同操作也可用于固定批处理脚本，外部 Agent 主要负责临时任务的规划与选材。

## 4.5 参考视频重建入口

参考视频输入 Codex 后，多模态模型根据画面与行为调用 melo-gcs CLI，创建项目、安排布局和动作，并关联所需元素。候选项目经 melo-gcs 渲染后，Agent 或设计师对照参考继续修订，最终保存为新的可执行项目。

近期内部重建试用采用记录为 GPT-6 Astra、推理强度为极高（extra-high）的配置。作者判断部分重建结果在视觉上接近参考视频。这是特定素材与配置下的定性观察，尚未报告对齐后的逐帧重建误差或系统性模型比较。

重建完成后，牌面、材质、堆叠和节奏修改继续使用相同的 melo-gcs 接口。保存的项目及元素关联成为后续制作的起点。

# 5 浏览器生产与按需 DCC 精修

## 5.1 Chromium GPU 是正式出片路径

melo-gcs 使用 Chromium 硬件 GPU 渲染，并以 Three.js 组织固定或受限视角的场景、材质、灯光和效果[9–11]。该路径已用于团队实际生产，批次及验收结果见第 7 节。

浏览器硬件渲染已在 NVIDIA GeForce RTX 3060 和 RTX 4090 上测试。第 7 节的 72 条视频均由melo-gcs 经 Chromium GPU 导出；显卡测试与批次耗时分别记录。

渲染以显式帧号驱动，项目决定动作和反馈的时间位置，机器执行速度不改变事件帧位。资源解析、帧输出与视频编码分别完成[1,12]。帧索引状态的复用支持重复的时间安排，但这些时序约束本身不证明不同浏览器版本、图形驱动或 GPU 下的像素完全一致。

## 5.2 无头执行与批量制作

无头模式下，Agent 或脚本提交项目和输出要求，制作进程完成资源解析、检查、渲染并返回结果。制作人员无需逐条打开工作台、操作时间线和启动导出，仍可通过浏览器预览或成片进行人工检查。

各变体保存外观、布局或节奏修改，经检查后输出视频。运行结果分别记录项目生成、资源就绪和视频完成等状态，局部问题返回相应步骤处理。项目保留供后续继续编辑。

CLI 任务以运行摘要关联输入项目、编辑操作和输出文件，无需依赖操作界面截图说明执行过程。

## 5.3 设计需求驱动的专业工程出口

设计师先审阅浏览器输出。满足要求的素材直接交付，能够在 melo-gcs 内解决的问题继续调整项目。浏览器表现无法满足设计要求时，导出 melo-gcs 项目，由外部 Agent 配合专用导入 Skill 构造或修改 AE／Blender 原生工程。

设计师可在原生工程中继续精修和渲染。专业工程交换映射与导入 Skill 属于内部实现，本报告说明这条路径的用途及交付形式。第 3.2 节所述的公开 melo-gcs 项目与回放契约，与这些私有 DCC 集成细节分开。

这一出口用于 melo-gcs 项目的后续精修。已有 AEP 或 Blender 源工程的直接改造，仍可在原软件内完成。

保持模式包括 frame-exact、semantic 和 rule-only[12]。frame-exact 允许外观变化，同时锁定回放时序与帧率，其名称不表示渲染像素完全相同。公开编译器在该模式下拒绝导演参数覆盖、帧率变更或缺少帧回放哈希的配方。semantic 保留玩法动作并允许演出重定时，rule-only 允许按适用规则生成新轨迹。玩法校验和资源检查处理声明的约束，成片媒体与创作用途仍需分别检查。版本化的能力与模式自述支持后续编辑。

# 8 设计经验与适用范围

## 8.1 先保留设计，再扩大复用

源工程保留了可直接编辑的制作关系。先改造完整工程，再从反复出现的需求中提取元素，可以让整理工作服务于具体任务。多模态召回用于选材，melo-gcs 项目记录元素在当前制作中的使用关系。

完整项目与局部元素适用于不同粒度的复用。首次整理的投入与后续派生的投入应分开考虑；对于单次或很少重复的任务，大量前置整理未必合算。

## 8.2 浏览器优先，专业软件按需求介入

在本文的固定或受限视角任务中，Chromium GPU 渲染承担实际交付，无头模式供 Agent 和脚本调度。专业软件提供存量资产，并在浏览器表现无法满足要求时承担精修。已有 DCC 工程也可直接在原软件中制作。

模型负责理解、选材和规划，项目与领域工具保存制作结果并执行后续修改。模型升级可扩展参考视频重建能力，已保存项目则继续通过既有接口编辑。

## 8.3 生产记录与质量结论的范围

72 条批次由 melo-gcs 经 Chromium GPU 导出，RTX 3060 和 RTX 4090 的测试用于确认硬件路径可用。历史批次缺少完整并发、逐阶段计时及与当前实现对应的版本记录，因而无法比较显卡性能或估计特定版本的收益。18 组内部存在复用关系，汇总比例不作为 72 个独立任务的抽样估计。

内部验收采用团队的投放标准，未报告逐人判定与评分者一致性，难以进一步分析评审分歧和评审组构成的影响。汇总数据无法分离结构、风格及其他要求对未通过结果的各自贡献，22 条未通过的melo-gcs 输出也没有逐项列明原因。第 6.2 节的三帧比较检查项目保存重载；参考视频重建是另一项定性观察，尚无统一时间对齐与画幅条件下的误差测量。

案例和生产记录支持浏览器在所述任务中的使用，适用范围不延伸到所有镜头、插件或游戏行为。

玩法与结构检查仍需配合设计师对创意和用途的判断。

本文介绍元素库的拆分、内容组织、召回和拼装功能，不评价检索算法。专业导入属于内部实现，公开文档不足以独立复现该转换器，也未验证任意专业工程与 melo-gcs 的无损往返。节奏控制用于编排演出，尚未拟合真实玩家行为；点击率、转化率、广告投入回报和音频质量不在评价范围内。

# 9 结论

本报告介绍了一套面向消除类游戏广告的可复用生产系统，将分散保存在专业源工程中的设计成果用于后续制作。完整工程可直接改造，适用内容也可提取到元素库，供多模态召回与拼装。melo-gcs项目保存玩法记录、演出时间和元素关联，原子 CLI 支持外观、布局、动作和节奏编辑。参考视频为缺少源工程的任务提供另一条项目接入路径。

melo-gcs 通过 Chromium GPU 和无头模式输出视频，浏览器表现无法满足设计要求时，再转入After Effects／Blender 原生工程精修。硬件渲染已在 RTX 3060 和 RTX 4090 上测试。报告的生产批次包含 18 组任务、每组 4 条，在两小时生产阶段内导出 72 条视频，其中 50 条（69.4%）通过内部综合验收并已投放。模型 Token 费用按第 7.3 节所述范围记录，每条输出低于 1 美元。

源工程布局改造、A001 保存重载及原创素材变体三个案例展示了已有设计和项目的持续使用，生产记录则说明浏览器的批量出片情况。将存量设计资源、可编辑项目、领域工具和按需专业精修结合，为直接视频生成之外提供了一条实际可用的广告素材生产路线。
